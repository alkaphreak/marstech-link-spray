# Checklist instances embed a snapshot of their template's items

## Context and Problem Statement

MLS-222 adds reusable checklists to sol4.space: a template (packing list, onboarding, release
steps) is defined once and instantiated many times, each instance tied to a context and tracking
its own progress. A template changes over time while instances created from it are still in
progress. How are templates, instances and items stored in MongoDB, and what happens to a running
instance when its template is edited?

## Considered Options

- Instance embeds a copy of the template's items at creation, template carries a version number
- Instance references a template version, item state stored apart from the item definitions
- Items in their own collection, linked to a template or an instance by id

## Decision Outcome

Chosen option: "Instance embeds a copy of the template's items at creation, template carries a
version number", because an instance then reads, updates and reports its progress from one
document, and editing a template can never alter a checklist already in use.

**Storage and ownership**

- Two collections, `checklist_templates` and `checklist_instances`. Each document belongs to the
  namespace of the `X-Api-Key` that created it, as for cron jobs (MLS-220). The key is required;
  a document outside the caller's namespace answers 404 (`findByIdAndNamespace`).
- Separate per-namespace limits for templates and instances, and a cap on items per list, under
  `mt.link-spray.checklist.*`: `max-templates-per-namespace` (default 50),
  `max-instances-per-namespace` (default 500), `max-items` (default 200). A template needs at
  least one item.
- Text fields are bounded: `title` and `context` 200 characters, item `label` 500, item `note`
  2000. Listing endpoints are paginated.
- Indexes created at startup by the service, as for cron jobs: `namespace` on both collections,
  `{namespace, templateId}` and `{namespace, context}` on instances. A failure is logged and does
  not block startup.

**Templates**

- A template holds a title and its ordered items: `itemId`, label, optional note. The embedded
  property is not named `id`, which Spring Data would map to `_id`.
- Item ids are UUIDs generated by the server; ids sent by a client are ignored. An item keeps its
  id when the template is edited, so instances can be compared with the current template.
- `version` is a Spring Data `@Version val version: Long? = null` field (null marks a new
  document, since ids are set by default). An update carries the `version` it read; the service
  copies it onto the entity before `save()`, so a stale version raises
  `OptimisticLockingFailureException`, mapped to 409 instead of overwriting a concurrent edit. Instances record the version they were created from,
  to show "template changed since" without ever resynchronising.

**Instances**

- An instance holds the template id and version it was created from, the template title copied at
  creation, a free-text `context` (trip, person, release tag, ...), and its own copy of the items,
  each with a status: `TODO`, `DONE` or `SKIPPED`.
- A status update is one atomic MongoDB update on the instance document, queried by id and
  namespace, matching the item by `itemId` with `arrayFilters`; concurrent updates of two items do
  not conflict. A matched document with nothing modified means an unknown item: 404.
- Progress is computed, not stored: `DONE / (total - SKIPPED)`, and 100 % when that denominator is
  0 (no item, or every item skipped).
- Deleting a template does not cascade: its instances keep their copied title and items, and
  `templateId` then points to a 404.
- The API is versioned by content negotiation (ADR 0001).

Out of this first slice, left to follow-up tickets: adding or removing items on a running
instance, dependencies between items, nested sub-checklists, per-item action URLs, assignment and
sharing, reminders through the cron API (MLS-220), JSON/Markdown import and export, the
`/checklist` web page.

### Consequences

- Good: one read returns an instance with its progress; no join and no item collection.
- Good: a template edit, or its deletion, leaves existing instances intact.
- Good: adding or removing items on a running instance later needs no model change, only atomic
  `$push`/`$pull` updates.
- Bad: a fix made to a template does not reach instances already created; they must be recreated.
- Bad: the first slice is reserved for `X-Api-Key` holders. Keys are issued by the admin, one
  namespace per key, so the deferred `/checklist` page, sharing and assignment cannot reuse this
  ownership model: a public page cannot hold a secret key, and sharing crosses namespaces. They
  need a user-level ownership model, decided in an ADR that amends this one.
- Bad: item definitions are duplicated in each instance. Fine under the 200-item cap, wrong for
  lists of thousands of items.

## Pros and Cons of the Options

### Instance references a template version, item state stored apart from the item definitions

- Good: no duplication of item definitions.
- Bad: every template version still referenced by an instance must be kept, and reading an
  instance needs a second lookup to merge definitions with statuses.

### Items in their own collection, linked to a template or an instance by id

- Good: an item can be queried or updated without loading its list.
- Bad: reading a checklist becomes a multi-document query, ordering and progress need aggregation,
  and deleting a list must cascade; nothing in the first slice needs item-level queries.
